# アート方針：QRいっき読み

- 版：1.1（2026-11-14 改定。改定理由と変更点は §8 と `docs/DESIGN_REVIEW_2026-11-14.md`）
- 決めた日：2026-11-14
- 出どころ：コンセプト・UXからの導出（利便性特化という本人の決定が起点）。v1.1 の色の具体化は本人の実機スクショ（v0.2.0）と本人の好み（深いネイビー＋柔らかい青白、ミニマルで静か）に基づく
- 対象：アプリ全体の UI（画面、パーツ、アイコン、動き）

## 1. 世界の言葉

- 雰囲気キーワード：**速い、正確、静か**
- やらない雰囲気：騒がしい、飾り過剰、エンタメっぽい、広告っぽい
- 一文で言うと：開いた瞬間に「道具として信頼できる」と感じ、操作の邪魔になるものが何も無い空気。

## 2. 根拠マップ（コンセプト → アートの選択 → 理由）

| コンセプトの要素 | アートの選択 | 理由 |
| --- | --- | --- |
| レジ前・現場で一息で終わらせたい | 装飾を排し、主役（カメラ／結果／大ボタン）だけを大きく | 見るものを減らすことが、そのまま速さになる |
| 複数コードを同時に扱う | 色は「検出できた」の合図にだけ使う。ピンは番号＋単色で統一 | 色数を増やすと、どれがどれだか分からなくなる |
| 誤タップ・詐欺 URL が怖い | 注意が必要な所だけ警告色を強く出す。平常時は静かな色調 | いつも騒がしいと、本当に大事な警告が埋もれる |
| 道具として長く使う | 流行の装飾を避け、OS 標準に近い形と余白 | 飽きず、OS の更新にも埋もれない |

## 3. 色の性格

- 主色の役割：主要な行動（推奨ボタン、検出の合図）にだけ使う。性格は**深いネイビー〜藍系**を軸とする（v1.1 で具体化）。ライトでは濃い藍が白地に立つ色、ダークでは柔らかい青白が藍黒の地に浮く色。彩度は中程度以下に抑え、「静かで正確」な道具の顔にする。Material 既定の水色はこのアプリの色ではない（v1.0 期の実装が既定色のままだったことが、実機スクショで「このアプリの顔が無い」と判明したための改定）。
- 補助色の役割：種別アイコンの区別など、意味の区別が必要な所だけ。色でなくアイコン形状の区別を優先し、色は二重の手がかりに留める。補助色も藍系のグレーを軸にし、色相を増やさない。
- 例外の暖色：お気に入りの星だけ琥珀色を許す（「大事なもの」の印として全画面で一貫させる）。これ以外の暖色は警告／エラー専用。
- 背景と文字の関係：背景は青みのある白〜薄い藍灰（ライト）／藍黒（ダーク）の中立色。純黒・純粋な灰は使わない（藍の世界に揃える）。文字は高コントラストを守る。QR のプレビュー表示は、読み取り精度のため常に白背景＋黒モジュールが既定（デザイン編集時も警告付きでのみ変更可、仕様 §7 FR-CREATE-04）。白い面も角丸スケールには乗せる。
- 色を増やすときの決まり：既存の役割（主行動／検出／警告／エラー／お気に入り）で表せない意味が出たときだけ追加を検討する。
- やらない色使い：画面ごとに色を変える、グラデーションの多用、意味のない色付きバッジ、フレームワーク既定色の流用。
- ※ 具体的な色コードはデザイントークン（`Theme.kt` の Qr 色定義、`docs/DESIGN_REVIEW_2026-11-14.md` のトークン表）を正とし、ここでは性格と役割を持つ。

## 4. 形の言語

- 角丸の方針：1つのスケールで統一する（v1.1 で固定：チップ 8dp／ボタン・入力欄・バナー 12dp／面とシート 16〜24dp）。鋭すぎず、丸すぎない「道具」の形。楕円や全丸はピンと初回ヒントのピルだけ。
- ボタンの形：主要ボタン（推奨行動）は高さ 52dp・角丸 12dp で全画面共通。補助ボタンも高さ 48dp・角丸 12dp・枠線のみで全画面共通とし、**幅は文言で決めず、置かれた列の幅に揃える**（並べた結果として潰れる・折り返す形は作らない。v0.2.0 の設定画面で実際に起きた崩れへの対応）。
- 線と境界：線より余白と面で分ける。境界線は一覧の区切りやツールバーの上端など必要な所だけ、最も弱い線色で。
- 影と立体：影なしフラットが既定。色の濃淡（トーン）で面を浮かせない。浮き上がるのはシートとダイアログだけ（OS 標準の扱い）。
- アイコンのタッチ：OS 標準に近い線画アイコンで統一する。自作アイコンは同じ線の太さ・角の処理で作る。アプリアイコンは QR のファインダーパターンを正しい比率で描いた白抜きマーク＋藍地とし、飾り文字は入れない。
- イラスト・写真：使わない。空状態（履歴ゼロ等）もイラストでなく一文＋次の行動ボタンで案内し、配置は画面の中央に置く（上に寄せて下を虚空にしない）。

## 5. 文字と密度

- フォントの性格：端末標準フォント。見出しだけ太さ（セミボールド）で個性を出し、書体は増やさない。
- 文字の階層の原則：主役（結果の要約・推奨ボタン）＞補助（内容プレビュー、種別）＞注記（生データ、日時）の3段まで。サイズと行間はトークンで固定し、画面ごとに勝手なサイズを作らない。
- 文言と改行の決まり（v1.1 で追加）：案内文は短く保ち、**末尾に1〜2文字だけが残る孤立行を作らない**（文を短くするか、2文に分けて組む）。設定の現在値などを示す要約文は、固定文でなく実際の値を映し、実態と文言がずれないようにする。空状態の文は中央寄せで組み、左右に偏らせない。
- 余白の決まり（v1.1 で追加）：余白は 4／8 の倍数だけを使う。画面の左右余白は全画面 16dp で統一し、セクション間は 24dp。画面ごとに余白の基準を変えない。
- 密度の方針：スキャン画面は最も空ける（カメラが主役）。宝箱の一覧は道具らしく詰めてよいが、1行の役割（種類／要約／日時）を崩さない。
- 1画面の情報量の目安：3秒で「何の画面か、次に何を押すか」が分かること。迷わせる要素が出たら足すのではなく引く。

## 6. 動きの性格

- 動きの性格：速く、短く。状態変化が伝わる最小限。
- 動きを入れてよい場面：検出できた瞬間のピン表示、シートの出し入れ、保存できた合図。意味を書ける動きだけ。
- やらない動き：飾りのループアニメーション、起動時のスプラッシュ演出、操作を待たせる遷移。
- 動きを減らす設定への対応：OS のアニメーション削減設定に従い、フェードのみに縮小する。

## 7. 良い例／悪い例

- 良い例：スキャン結果シート（主役＝推奨ボタン1つ、他は全部補助に降格している状態）。
- 悪い例：ホーム画面に機能アイコンをずらりと並べたランチャー型（主役が無く、毎回探すことになるため採用しない）。
