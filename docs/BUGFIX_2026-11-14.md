# 不具合総点検・修正記録（2026-11-14、v0.3.1）

本人の指示「不具合をすべて直して」を受け、全 Kotlin ソースを通読し、純粋ロジックは
単体テストで潰しながら点検した記録。機能追加・デザイン変更はしていない
（修正に伴う最小のガード・文言のみ）。

重大度：重大＝クラッシュ／データ喪失の経路、中＝機能が動かない・誤動作、
軽微＝表示・利便性・データの小さな不整合。

## 修正した不具合

### 重大

- **B-01 保存データの読み込みが壊れやすく、ID重複で画面が落ちる**
  - 症状：`library.json` の要素が1つでも壊れていると宝箱全体が空に見え、その後の
    保存でファイルごと上書きされて復旧不能になる。ID が重複したバックアップを
    取り込むと、宝箱一覧のキー重複でアプリがクラッシュする。
  - 原因：`Store.load()` が配列要素の変換例外で全体を失敗扱いにしていた。
    読み込み側に ID の重複排除がなかった。`parseBackup()` は要素の形式を
    検証していなかった。
  - 修正：要素ごとに変換し、壊れた要素だけ読み飛ばす。読み込み・取り込みの
    両方で ID の重複を排除する。ファイル全体が読めない場合は
    `library.json.corrupt` へ退避してから空で始める（上書きで消さない）。
    バックアップ検証として「rawValue キーを持たない要素を含むファイル」は
    バックアップではないとして弾く（他アプリの JSON 等の誤取り込み防止）。

- **B-02 保存の書き込み例外でアプリが落ちる／無言で保存されない**
  - 症状：端末の空き容量不足等で書き込みに失敗すると、UI の操作ハンドラまで
    例外が伝播してクラッシュする。一時ファイルからの rename が失敗した場合は
    何も言わず保存されない。
  - 原因：`Store.saveAll()` に例外処理がなく、`renameTo` の成否を見ていなかった。
  - 修正：書き込み全体を例外処理で包み、rename 失敗時は直接コピーへ
    フォールバックする。

### 中

- **B-03 Wi-Fi の暗号化方式を取り違える（"Wifi:" 等の混在ケース）**
  - 症状：`Wifi:T:WPA;S:…` のように接頭辞の大小が混ざった QR を読むと、
    種別は Wi-Fi になるのに暗号化方式が「なし（nopass）」と表示され、
    接続もオープンネットワークとして試みられる。
  - 原因：`parseWifi()` の接頭辞除去だけが大文字小文字を区別していた
    （分類側は区別しない）。
  - 修正：接頭辞除去を大小区別なしにする。単体テスト追加。

- **B-04 スキームなしURLが「開く」ボタンで開けない**
  - 症状：`example.com/path` のような裸URLは URL 種別に分類されるのに、
    「ブラウザで開く」を押すと「開けるアプリが見つかりませんでした」になる。
  - 原因：スキームのない相対 URI のまま ACTION_VIEW に渡していた。
  - 修正：`parseUrl()` が返す「開く用URL」には、スキームがなければ
    `https://` を補う。単体テスト追加。

- **B-05 ポート付き裸URLを URL と判定しない**
  - 症状：`example.com:8080/path` がテキスト扱いになり、開く導線が出ない。
  - 原因：裸URL判定がホスト部の末尾＝TLD とみなしており、`:8080` を
    含むため英字チェックで落ちていた。
  - 修正：TLD 判定の前にポート部を落とす。単体テスト追加。

- **B-06 SMS の本文が「メッセージを作成」に引き継がれない**
  - 症状：本文付き SMS コード（`smsto:番号:本文`、`sms:番号?body=…`）を
    読んでも、作成画面に本文が入らない。
  - 原因：結果シートが番号だけを取り出して `smsto:` を組み直していた。
  - 修正：本文を取り出す処理を追加し、`sms_body` として渡す。単体テスト追加。

- **B-07 メールの件名・本文が引き継がれない**
  - 症状：`mailto:宛先?subject=…&body=…` のコードでも件名・本文が空の
    作成画面が開く。MATMSG 形式の SUB/BODY も使われていなかった。
  - 原因：結果シートが宛先だけを取り出して `mailto:` を組み直していた。
  - 修正：mailto は元の URI をそのまま ACTION_SENDTO に渡す。MATMSG は
    TO から宛先を作り、SUB/BODY を件名・本文として渡す。

- **B-08 vCard / iCalendar のエスケープが読み取り側で残る**
  - 症状：自作の連絡先QR（名前「山田,太郎」→ `FN:山田\,太郎`）を読み直すと、
    名前に `\,` が残って表示され、そのまま連絡先に登録される。予定の
    タイトル・場所でも同様。
  - 原因：書き出し側はエスケープするのに、読み取り側の行値取得が
    エスケープを解除していなかった。
  - 修正：行値の取得時にテキスト値のエスケープ（`\,` `\;` `\n` `\\`）を
    解除する。単体テスト追加。

- **B-09 不正な予定日時を繰り上げ解釈してしまう**
  - 症状：`DTSTART:20261301T103000`（13月）のような外部コードで、
    翌年1月に繰り上がった日付でカレンダー登録画面が開く。末尾に
    余分な文字がある値も受理していた。
  - 原因：`QrFactory.parseIcalDateTime()` が lenient な SimpleDateFormat で
    部分一致のまま解析していた。
  - 修正：非 lenient ＋文字列全体を消費した場合だけ受理する
    （既存の入力検証と同じ方式）。単体テスト追加。

- **B-10 WIFI: 形式のエスケープ不足（引用符）**
  - 症状：SSID やパスワードに `"` を含むと、他のスキャナが誤解析する
    壊れた WIFI: ペイロードが生成される。
  - 原因：ZXing の WIFI 形式でエスケープ対象とされる文字は
    `\` `;` `,` `:` `"` の5つだが、`"` が抜けていた。
  - 修正：`escapeField()` に `"` のエスケープを追加。単体テスト追加。

- **B-11 予定の「終了が開始より前」でも QR が作られる**
  - 症状：終了を開始より前にして作った予定QRがそのまま生成され、
    読み取り側でも終了＜開始のままカレンダーへ渡る。
  - 原因：日時の形式チェックはあったが前後関係を見ていなかった。
  - 修正：生成側は終了＜開始なら payload を作らない。フォームには
    終了欄にエラーを表示する。読み取り側（外部コード）は、終了＜開始なら
    開始＋1時間に補正してから渡す（登録画面が壊れないためのガード）。

- **B-12 カメラがタブを離れても動き続ける**
  - 症状：スキャン以外のタブに移ってもカメラと解析が Activity の
    ライフサイクルに紐付いたまま動き続け、他の画面でも新しいコードを
    検出して振動しうる。解析用 Executor も解放されない。
  - 原因：`bindToLifecycle` の対象が画面（コンポジション）ではなく
    Activity で、画面を離れる際の unbind がなかった。
  - 修正：画面を離れたらカメラを unbind し、Executor を終了し、
    スキャナを閉じる。破棄後にバインド完了が届いた競合も、破棄フラグで
    その場で unbind して塞ぐ。

- **B-13 PNG 保存が失敗しても成功表示になる**
  - 症状：MediaStore への保存で出力先が開けなかった場合などに、
    何も保存されていないのに「写真に保存しました」と表示される。
  - 原因：`openOutputStream` の null と `Bitmap.compress` の成否を
    見ていなかった。
  - 修正：開けない・圧縮失敗は例外として失敗表示にする。共有側も同様。

- **B-14 API 28 以下で PNG 保存が常に失敗し、ギャラリーにも出ない**
  - 症状：API 26〜28 の端末では「保存に失敗しました」になる。保存できた
    場合もメディアスキャンされずギャラリーに表示されないことがある。
  - 原因：WRITE_EXTERNAL_STORAGE は実行時許可が必要だが、アプリは
    カメラ以外の許可を一度も求めていない。ファイル書き込み後の
    メディアスキャンもしていなかった。
  - 修正：許可がない場合は許可不要のアプリ専用 Pictures フォルダへ保存し、
    どちらの経路でも保存後にメディアスキャンを実施する。

- **B-15 画像の読み取りがメインスレッドで固まる**
  - 症状：共有・ピッカーから大きな写真（共有インテント経由を含む）を
    読むと、デコードがメインスレッドで走り、画面が固まる／ANR・
    メモリ不足の経路になる。
  - 原因：`InputImage.fromFilePath` を画面スレッドから直接呼んでいた。
  - 修正：IO スレッドで読み込み、失敗時は従来どおりメモ表示にする。

- **B-31 解析プロキシが閉じられずスキャンが止まる経路**
  - 症状：`InputImage.fromMediaImage` が例外を投げた場合、そのフレームの
    ImageProxy が閉じられず、以降の解析が詰まる。
  - 原因：変換処理が例外処理の外にあった（通常経路の close は
    完了リスナーで担保されている）。
  - 修正：変換〜処理開始を try/catch で包み、例外時も必ず閉じる。

### 軽微

- **B-16 GEO の座標文字列がそのまま payload になる**
  - 症状：`3.5e1` のような指数表記や `35.` が `geo:` URI に入り、
    他の地図アプリが解釈できない。
  - 原因：検証済みの数値ではなく入力文字列で組み立てていた。
  - 修正：検証済みの Double を文字列化して組み立てる。単体テスト追加。

- **B-17 URL 種別で「https://」だけでも作れてしまう**
  - 症状：スキームだけで中身のない QR が作れる。
  - 修正：スキームの後が空なら payload を作らない。単体テスト追加。

- **B-18 VEVENT に必須項目（UID / DTSTAMP）がない**
  - 症状：RFC 5545 で VEVENT 必須とされる UID と DTSTAMP がなく、
    厳格な外部カレンダーが予定を取り込めないことがある。
  - 修正：生成時に UID と DTSTAMP（UTC）を付ける。単体テスト追加。

- **B-19 QR 容量超過のとき PNG ボタンが無反応**
  - 症状：長文すぎて QR 化できない内容では、「PNGを保存／共有」を
    押しても何も起きない（成功も失敗も表示されない）。
  - 原因：bitmap が null の場合を呼び出し側が握り潰していた。
  - 修正：生成できない場合は「内容が長すぎてQRを生成できませんでした」
    と理由を表示する。あわせて PNG の生成・保存・共有を
    バックグラウンド実行にし、ボタン連打や大きな画像でも画面が
    固まらないようにした。

- **B-20 再編集で保存すると作成日時が変わってしまう**
  - 症状：保存済みQRを再編集して保存すると createdAt が現在時刻に
    なり、一覧の並び（新しい順）が変わり元の日時が失われる。
  - 原因：置き換え時に新しい Entry の日時をそのまま使っていた。
  - 修正：置き換え時は元の createdAt を保持する。

- **B-21 別種別の入力が保存データに混入する**
  - 症状：URL 種別で打った内容が、種別を変えて保存した連絡先などの
    fields にも（同名キーのため）紛れ込む。
  - 原因：フォームの入力マップが全種別で共有され、丸ごと保存されていた。
  - 修正：保存時は現在の種別の項目キー（＋暗号化方式等の付随キー）だけを
    抜き出して保存する。

- **B-22 種別情報のない作成済み項目の「再編集」が固まる**
  - 症状：createType を持たない CREATED 項目（手作り・壊れた
    バックアップ由来）の再編集を押すと何も起きず、編集状態も残る。
  - 修正：種別がない場合も編集状態を消費して通常表示に戻す。

- **B-23 フォルダのチップ行が画面外に切れる**
  - 症状：フォルダが増えると、右側のチップが画面外に出て選べない。
  - 修正：チップ行を横スクロール可能にする。

- **B-24 端末設定でカメラ許可を変えて戻っても反映されない**
  - 症状：一度拒否したあと端末設定で許可して戻っても、許可を求める
    画面のままになる（ボタン再押下では復帰する）。
  - 修正：画面復帰（ON_RESUME）のたびに許可状態を再確認する。

- **B-25 カメラ再接続時に懐中電灯・ズームが再適用されない**
  - 症状：タブ往復などでカメラがつなぎ直されると、表示はライトON・
    ズーム変更済みなのに実際は初期状態に戻っている。
  - 修正：バインド直後に現在のライト／ズーム状態をカメラへ適用する。

- **B-26 画像読み取りのメモ表示が残り続ける**
  - 症状：「画像から○件見つけました」の表示が、カメラで読み始めても
    ツールバーの下に残り続ける。
  - 修正：カメラで検出が始まったらメモを消す。

- **B-27 共有 PNG のファイル名が固定**
  - 症状：共有のたびに同じファイル名で受け側のキャッシュと競合しうる。
  - 修正：タイムスタンプ付きの名前にする。

- **B-28 プレビュー生成が表示サイズに対して過大**
  - 症状：小さなプレビューでも 720px で毎回生成され、入力のたびの
    再生成が重い。
  - 修正：表示サイズに応じた解像度（上限 720px）で生成する。

- **B-29 未使用 import の警告**
  - 症状：CreateScreen の `Icons.Filled.Call` など、未使用 import が残る。
  - 修正：コンパイラ警告を確認して一掃する。

- **B-30 BOM 付きの入力を取りこぼす**
  - 症状：先頭に BOM（U+FEFF）が付いた vCard 等がテキスト扱いになる。
  - 修正：分類の先頭で BOM を除去する。単体テスト追加。

## 疑い（推測の域を出ないため、直さず記録のみ）

- **S-1 Wi-Fi の WPA3(SAE) 提案方式**：暗号化が WPA3 のとき WPA2
  パスフレーズで提案している。移行モードの AP では動くが SAE 専用では
  失敗しうる。実機と AP の組み合わせに依存するため未変更。
- **S-2 座標抽出の誤認余地**：共有テキスト中の「@数字,数字」は座標として
  拾う設計（D-4）。値域チェック等で多くは弾かれるが、座標らしく見える
  通常文を完全には区別できない。仕様の範囲として記録のみ。
- **S-3 空のバックアップ「[]」の取り込み**：「空の宝箱のバックアップ」
  と区別できないため、取り込むと置き換えで空になる。置き換え方式という
  仕様どおりの挙動であり、誤取り込み対策は B-01 の形式検証までとした。
- **S-4 iCalendar の行折り返し**：75 オクテットでの行折り（folding）は
  未実施。多くのパーサは未折り返しを受理するため未変更。
- **S-5 保存 JSON の読み書きはメインスレッド**：アプリ内だけの小規模な
  JSON が前提。非同期化は書き込み順序とデータ喪失リスクを変えるため
  今回は行わない（画像デコードのような大きな処理は B-15 で分離済み）。
  バックアップ書き出し／読み込みのファイル IO も同様に小規模前提で据え置き。

## 点検済み・問題なし（仕様と照合した観点）

- **自動削除の境界と対象**：ちょうど30日の項目は保持され、30日を
  超えたら削除される（cutoff 以上を保持）。作成済みQRは対象外。
  お気に入り済みの読取履歴も削除対象だが、仕様 FR-LIB-02 と設定画面の
  文言（「読取履歴だけが対象」）にお気に入りの例外規定はないため、
  現状は仕様どおりと判断した。
- **「全部を履歴に保存」と自動保存設定**：自動保存 OFF でもボタンは
  押せる。FR-SCAN-07 の文面どおり（設定はタップして開いたときの
  既定動作のみを指す）で整合している。
- **振動 OFF の反映**：カメラ検出・画像読み取りの両経路とも
  `handleDetected` 内のチェックを通るため、OFF が両方に効く。
- **重複 ×n のカウント**：フレーム単位で集計し直すため、フレームを
  またいで増え続けることはない。保持中（見失い中）のコードも前回値を
  維持する。
- **平滑化の境界**：座標が取れないコード（boundingBox なし）は
  座標 -1 として扱われ、ピンは描かれず位置も引き継がない。
  フレームサイズが変わった場合も引き継がない。
- **Wi-Fi 接続のバージョン差**：API 29 未満は案内文で安全に終了する。
  WEP は未対応を明示して終了する。WPA でパスワードが空の場合は
  例外を握って失敗表示になる。
- **結果シートの Intent 群**：ブラウザ・電話・メール・SMS・連絡先・
  カレンダーは `runIntent` が ActivityNotFoundException 等を握って
  案内表示になる（裸URLの不発は B-04 で修正）。
- **共有インテントの受け口**：読めない画像 URI・画像でないファイルは
  例外を握ってメモ表示になる。テキストの null／空は無視される。
  起動中の共有（onNewIntent）も同じ処理を通る。
- **予定の日時のタイムゾーン**：生成・読み取りとも「浮動時刻＝端末の
  ローカル時刻」として一貫している（QR の予定形式の通例どおり）。
- **検索の重さ**：宝箱の検索は件数に比例する単純な文字列照合のみで、
  想定件数（数千件規模まで）では問題にならない。
